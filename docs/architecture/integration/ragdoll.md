# 布娃娃身体接管

> **适用问题**：玩家死亡布娃娃的可见身体如何由 KINETIC 模型绘制、关节如何保持连续与受限、性能预算与降级边界；**不包含**：提供方的物理与网络机制，也不重新定义联动业务范围（见[联动决策](../../product-decisions/decisions/death-ragdoll.md)）。

接入点与可选降级总则见[游戏与扩展接入](README.md)。本页只描述当前机制：KINETIC 读取提供方已经算好的刚体位姿，用自身骨架绘制身体，并补齐刚体无法表达的细分关节。

## 职责划分

| 关注点 | owner |
|---|---|
| 刚体数量、形状、碰撞、冲量、击退、生命周期 | 布娃娃提供方 |
| 可见身体使用的模型、贴图与关节运动 | KINETIC |
| 护甲、饰品、血迹等图层 | 布娃娃提供方原有路径 |
| 原版人形基础部件是否跳过 | KINETIC 逐帧建立的接管状态 |

提供方对玩家固定使用六段人形骨架，其刚体数量与部件枚举是线协议的一部分，无法承载作品模型的完整关节。因此 KINETIC 不扩展提供方骨架，而是把它的刚体位姿当作输入：刚体朝向驱动六根大关节骨骼，其余关节由 KINETIC 侧的次级动力学补全。

## 死亡入口

玩家在客户端**收不到** `LivingDeathEvent`：该事件只在 `LivingEntity#die` 中发出，而客户端的 `LivingEntity#hurt` 在 `level().isClientSide` 时立即返回，`handleEntityEvent(3)` 又显式跳过玩家。因此死亡入口观察**客户端玩家的死亡状态**（每 tick 检查 `isDeadOrDying`），而不是监听事件；同一个实体在一次死亡中只处理一次，复活或离开世界后清除记录。

死亡当刻先捕获 KINETIC 当前骨骼姿态并注入提供方；随后客户端优先等待服务端权威布娃娃及其同步。等待 6 tick 仍未见布娃娃时，KINETIC 才用保留的致死 `DamageSource` 走 `createFromEntity(entity, damageSource)` 兜底生成。姿态注入与客户端兜底都发生在客户端玩家实体移除（死亡 20 tick 后）之前；带来源的兜底入口同时保留致死一击方向与冲量。

实体被移除后，接管状态改为依赖死亡瞬间的快照（模型来源、宽高缩放、贴图），不再依赖仍然存活的 capability；模型资源被回收导致原生提取失败时，捕获异常并降级回提供方的原版人形，而不是每帧重试。

## 姿态映射

一具布娃娃对应一份 KINETIC 侧状态，持有独立于玩家的模型实例与骨骼属性数组，因此接管期间不会改写玩家自身正在使用的姿态。

- **大关节**：由刚体世界朝向反解局部旋转 `L = (q_torso · C)⁻¹ · Q_part`。
- **常量偏移 `C`**：在接管的第一帧由 `C = q_torso(0)⁻¹ · Q_part(0) · L_captured⁻¹` 解出。它把提供方坐标系与模型坐标系之间的任何常量差异（含双方各自的角度约定）一次性吸收，并使首帧局部旋转精确等于死亡当刻捕获的角度。这是「不跳变」的机制来源，而不是靠调参逼近。
- **细分关节**：肘、腕、膝、踝与披风等直接写自身局部角度，父级链路由原生 FK 负责。
- **未驱动通道**：位置、缩放、可见性与颜色保留捕获姿态的值，因此模型自身的隐藏标记与着色不会被接管破坏。

模型定位以躯干刚体为锚：躯干中心沿躯干自身「下」方向偏移半个躯干高得到髋部，模型根骨骼枢轴落在此处，因此不会上下错位。

## 细分关节运动

细分关节按固定步长的阻尼积分，每步的力矩为重力下垂、父级线加速度带来的惯性滞后与阻尼之和：

- 重力与惯性项在**父级坐标系**中计算，力臂取该骨骼的静止方向，因此父级刚体如何翻滚都会产生合理摆动。
- **没有回位弹簧**：关节不会被拉回死亡瞬间的姿势，而是像钟摆一样摆到重力方向并停在那里；重力项本身就是恢复力矩，阻尼比 ζ=c/(2√gravity) 约 0.6~0.75，摆动一两次就停下。这样肘、膝、手、脚表现的是自然摆动，而不是「弹回死亡姿势」。
- 硬限制放宽到包含死亡姿态角度，保证首帧完整保留；积分越界时按完全非弹性处理并清零该轴速度，避免贴边抖动。
- **铰链关节**（肘、膝）只允许绕自身轴转动，另外两个轴锁死在死亡当刻的角度，因此不会出现反关节或扭转。
- **防穿透**：两层，都只作用于 KINETIC 驱动的细分关节，大关节由提供方求解器自身的关节锥与碰撞负责。
  - 躯干按提供方的半长宽构成包围盒，末端进入该盒时获得一个把末端推离的角速度增量。
  - 地面：调用方每帧传入尸体所在位置的地表高度，末端低于地表时同样获得一个把末端抬起的角速度增量。拿不到世界信息时传入 `NaN`，该层整体失效——宁可不管，也不用猜出来的平面去掰关节。

刚体运动历史由相邻帧的位置与朝向差分得到；若两帧间隔过大（例如休眠后重新被撞动），历史按新起点重建，避免用陈旧位置算出的速度与加速度把关节甩飞。

## 绘制与让位

KINETIC 在实体绘制阶段之前建立本帧接管状态并绘制自己的身体；提供方随后绘制该布娃娃时，其玩家身体路径的基础部件被跳过，护甲、饰品与血迹等其它图层照常绘制。跳过只针对玩家布娃娃，且只在该布娃娃确实已被接管时生效。

**接管的前提是"让位链路确实活着"。** 让提供方跳过身体的三个注入点都是 `require = 0`：提供方改了签名时它们会静默失配，而 KINETIC 的绘制由独立的事件监听驱动、不受注入点影响。若不做任何判断，提供方照旧画自己的原版人形、KINETIC 又画一份，同一具尸体就会出现**两份身体**。因此只有"见过注入点真的被调用过"之后才允许接管；失配时 KINETIC 一次都不画，完整回退到原版人形。代价是会话里第一具布娃娃晚一帧被接管，那一帧由提供方画。

**每一个"本帧不画"的出口都必须同时放掉接管状态**，否则会出现"提供方以为 KINETIC 在画、KINETIC 又不画"的空档：超出绘制距离、连躯干位姿都拿不到、姿态提取失败、模型不可用、贴图不可用——这些分支都会丢弃状态，让提供方下一帧恢复原版人形。漏掉距离那一条的后果尤其明显：一段距离带里尸体完全不可见，而护甲照常绘制，看起来是浮空盔甲。距离本身取自提供方的配置，见[绘制距离与快照保留](#绘制距离与快照保留)。

贴图复用实时渲染同一条链路，因此皮肤类模组选中的皮肤对尸体同样生效。

## 状态与回收

接管状态按布娃娃标识存活：模型实例变化、提供方不再返回该布娃娃、玩家不可用或姿态提取失败时，状态被丢弃并释放其原生模型状态。玩家不可用或骨架无法映射时不做接管，直接让提供方按原版人形绘制。

**逐帧的刚体位姿缓冲由状态自己持有**，不是渲染器里的一份共享静态数组：提供方对断肢（`renderHiddenPartMask`）会返回 `null` 位姿，此时保留"上一帧的值"才有意义——共享数组保留的可能是**另一具布娃娃**的位姿，同屏两具尸体时断肢会被画到别人的位置上，而且那具尸体的宏观偏移会被永久解错。

**回收覆盖所有出口**：退出世界（`level`/`player` 为空）、接管被关闭时都会主动清空状态与捕获快照，而不是等下一次成功绘制时才顺便清理；接管关闭时也不再捕获死亡姿态，否则每死一次就多留一份模型引用与骨骼数组，整局都不会回收。

## 绘制距离与快照保留

绘制距离与存活时间只有提供方一个权威，KINETIC 不再自己配一套。

两边各有一个距离时，只要不相等就会在同一具尸体上打架：KINETIC 更近，就会在自己的距离外把尸体交回给原版人形（模型跳变）；KINETIC 更远，就会在提供方已经停止绘制之后继续画（隐形尸体）。因此 KINETIC 直接读提供方的客户端绘制距离，只在读不到（老版本没有该字段）时退回提供方文档里的默认值 128，而不是 KINETIC 原来的 64。

死亡姿态快照的保留时长同样跟随提供方的存活时间：快照只有在对应布娃娃还存在时才有用，提供方清掉布娃娃之后继续留着只是白占内存（每个玩家一份模型引用加一份骨骼数组）。tick 到毫秒的换算与余量在 `RagdollTuning` 里，可以在没有提供方、也没有渲染环境的单测里断言。

## 死亡相机与绑定

提供方自带一个死亡相机：在它自己的 `ViewportEvent.ComputeCameraAngles` 处理器里把相机挂到尸体的头部刚体上。该事件晚于 `Camera#setup`，而真实相机的绑定写入发生在 `Camera#setup` 内，因此**两者同时开启时以提供方为准**，不存在争夺同一帧最终位姿的问题。

KINETIC 在这里补的是另外两种情形：

- 提供方关掉了死亡相机时，仍然有一份由模型真实眼睛位置驱动的绑定；
- 玩家模型在布娃娃构造完成后会被提供方从渲染里摘掉，若继续绑定玩家，真实相机捕获不到任何几何，连续失败若干帧后会把整个模组关掉（表现为死亡瞬间绑定失效并弹出失败提示）。

因此死亡后绑定来源切换为这具布娃娃：`KineticRagdollRenderer#bindSource` 给出与绘制完全同一条链的「模型局部 → 世界」矩阵、法线矩阵与原生骨骼姿态，再减去真实相机将要加回去的「相机实体插值位置」。切换只在 KINETIC 确实接管了这具尸体时发生，其余情况仍走玩家模型那条路径。完整链路见[真实相机绑定](camera-binding.md)。

绘制侧还有一条与之配套的约束：相机正处在尸体脑袋里时（提供方的 `ClientRagdollCamera#isHeadHidden`）必须**强制启用背面裁剪**。KINETIC 整具尸体只有一次原生提交，分不出"只画身体"，但强制裁剪后头骨内壁是背面、直接被剔掉，效果与提供方丢掉头部一致：看得见肢体，看不见自己的颅内。默认配置本来就裁剪背面，所以这条只在用户关掉 `CullBackFaces` 时改变画面。

## 性能预算

每帧每具布娃娃的成本被限制为：一次骨骼属性数组拷贝、六次四元数反解、至多三个固定子步的阻尼积分、若干次防穿透检测与一次原生 extract，随后复用与普通玩家渲染相同的原生绘制路径。刚体与姿态都静止时跳过积分、姿态重建与 extract，直接复用上一次的模型状态；超出提供方绘制距离的布娃娃不参与绘制。受伤外观是这条路径上的第二遍绘制，同样受该距离约束。

## Ragdollified 1.2.2 的接口核实与让出规则
Ragdollified 是可选运行时依赖：构建以 1.2.2 API 编译，但不打包提供方；运行时先检查模组是否安装，
兼容入口再反射解析可选 API，渲染层只在提供方可用时注册。本文记录**对着 1.2.2 的 jar 逐项核实过**的接口面，
以及"什么时候让出死亡动画"这条容易出事的规则。

### 用到的接口（对着 1.2.2 的 jar 逐项核实）

| 类 | 成员 | 用途 |
| --- | --- | --- |
| `api.RagdollifiedApi` | `spawn(LivingEntity)` | 触发入口 |
| `api.RagdollifiedApi` | `hasRagdoll(Entity)` / `hasRagdoll(int)` | 判断布娃娃是否真的存在 |
| `api.RagdollifiedApi` | `setEntityHidden(int, boolean)` / `isEntityHidden(int)` | **1.2.2 新增**：隐藏/恢复尸体 |
| `config.RagdollifiedConfig` | `isRagdollEnabledFor(String, boolean)` | 玩家布娃娃是否被配置启用 |
| `config.RagdollifiedConfig` | `RAGDOLL_LIFETIME` | 清除时间；驱动死亡姿态快照保留时长 |
| `config.RagdollifiedConfig` | `RENDER_DISTANCE` | 提供方布娃娃绘制距离 |
| `MobPoseCapture` | `storePose(int, MobPose)` | 注入死亡瞬间姿态 |
| `client.ClientRagdollManager` | `createFromEntity(LivingEntity, DamageSource)` | 带致死一击的生成 |
| `client.ClientRagdollManager` | `hasPendingOrActiveRagdoll(int)` | 判断是否已排队 |
| `client.ClientRagdollCamera` | `isHeadHidden(int, RagdollTransform)` | 依据布娃娃躯干变换判断相机是否在头部内 |

> 1.2.2 的 `RAGDOLL_LIFETIME` 与 `RENDER_DISTANCE` 使用自带 `ConfigSpec`，而不是 Forge 的
> `ForgeConfigSpec`。KINETIC 通过共同的 `Supplier#get()` 读取两者，因此快照 TTL 和绘制距离
> 跟随用户在 Ragdollified 中的实际配置。

## 2. 为什么"死了直接消失"（1.2.2 的行为变化）

1.2.2 的客户端 `ClientDeathHandler.onLivingDeath` 会按客户端模型类型过滤本地生成；KINETIC 换过渲染器时，
该路径可能判为 `UNSUPPORTED`。但这不等于服务端不生成：服务端玩家路径将模型类型设为
`HUMANOID_STANDARD`，并通过 spawn 包同步布娃娃。客户端玩家通常收不到 `LivingDeathEvent`，
所以 KINETIC 必须观察死亡状态、提前注入姿态，并等实际布娃娃同步到来。

若仅按配置立即让出动画，会在服务端 spawn 包到达前丢失尸体表现；若立即在客户端重复 spawn，
又会与服务端实体重复。

**修正后的规则**：

```java
shouldYieldDeathAnimation(entity)
  = 没被登记为回退
 && (我们自己 spawn 成功排队 || 提供方那边 hasRagdoll 为真)
```

也就是**必须真的存在（或在途）才让出**，而不是按配置猜。

## 3. 回退链

1. 死亡当刻：`handleClientDeath` 只注入姿态，并登记 6 tick 后的客户端兜底；此时不在客户端立即 `spawn`；
2. 等待期间每 tick 先查询服务端同步来的 `hasRagdoll` / `hasPendingOrActiveRagdoll`；若已存在就取消兜底；
3. 6 tick 后仍无服务端布娃娃，才由客户端调用带致死来源的生成入口；成功后登记 `PENDING_VERIFY`，再验证 20 tick；
4. 验证超时仍不存在 → 登记 `FALLBACK_DEATHS` 并调用 `setEntityHidden(id, false)`；随后恢复 KINETIC 死亡动画。

最坏情况因此从"玩家凭空消失"变成"播正常死亡动画"。

## 4. 测试

- `RagdollDeathYieldTest`：客户端死亡入口不得立即 spawn，必须先等服务端；超时兜底需先查存在性；成功排队后要验证、失败要登记回退、让出判定要求真实存在，回退路径恢复可见性。
- `RagdollTuningTest`：验证 `Supplier#get()` 数值读取兼容 Forge 与 Ragdollified 1.2.2 的配置对象，并覆盖缺失、非数值和异常值。

### 1.2.2 反编译结论：布娃娃是服务端权威的

对着 `ragdollified-forge-1.20.1-1.2.2.jar` 反编译（Vineflower）后确认：

- `PhysicsHooks.spawnRagdoll` **只在服务端跑**（`if (!entity.level().isClientSide)`），
  生成后由 `ServerRagdollSyncManager` + `RagdollSpawnPacket` 同步给客户端；
- 玩家分支里 `modelType` **写死** `HUMANOID_STANDARD`，**不看客户端渲染器**——
  所以 KINETIC 换过模型不影响玩家布娃娃；
- 服务端用 `DeadPlayerKeepMixin` 拦住 `LivingEntity.tickDeath`，尸体实体不会被移除；
- `ClientDeathHandler.onLivingDeath` 那条客户端路径只在客户端真的收到
  `LivingDeathEvent` 时才跑，玩家通常是拿不到的。

因此 KINETIC 的客户端 spawn **只能是兜底**：死亡当刻先只注入姿态，`DEFERRED_SPAWN`
等 6 tick；到点仍没有服务端那份（`hasRagdoll` / `hasPendingOrActiveRagdoll` 都为假）
才在客户端补一个，再进 20 tick 的验证队列。顺序反了就会在同一具尸体上出现两份布娃娃。

姿态注入用的 `MobPose(Map)` 与 `PartPose(float,float,float)` 在 1.2.2 里仍然存在。
